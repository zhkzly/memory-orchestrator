## 已定位的问题

1. **有工具动作，缺工具返回。** 原136事件经有界选择后覆盖17事件，普通action总在普通result前，catalog又重用同序。已提供业务正文只有1条订单；库存、商品、客户实际返回都不在正文，若干已选GET的结果连可补读引用也没有。容量探针返回的模型明确承认缺业务证据，只提炼泛化检查流程。修改为同episode/call_id成组、跨本地时间阶段覆盖；目录优先补缺失返回及重要长材料续段。
2. **业务字段被误当失败锚点。** 裸exception匹配customer_exception，导致正常模板/备忘录从中间截起。修正词边界/实际异常线索；旧磁盘派生hint在读阶段核验，原档案和旧checkpoint保留。
3. **Actor看不到当前剩余轮次。** 每轮只有初始上限6，continued第6轮仍做GET。现在每次payload临时包含一条当前HOST_EXECUTION_STATE，末轮明确没有之后的模型交互；不累积旧提示、不自动补答案。六轮/128工具和评分不变。这是执行器上下文改进，不算memory收益。
4. **检查义务的范围披露太晚。** 旧真实CSV canary已证：N07缺evaluation_scope，N08才收到；模板没完整说明check_plan全部必需、诊断/提案并集、null阻发布。N07现在提前收到范围，模板明确后果并区分知识不足与暂缺验证材料。仍允许有依据的待验证候选，不禁null/不降低发布门。GDPevo本轮的check_ref都已绑定，不能把此项说成它的本次分数原因。
5. **超时与上下文质量须分开。** 首次extract约61004消息字符在45.05秒超时，使用相同完整payload的120秒上限探针在20.94秒返回，且19200/20090输入tokens被缓存。不能据此声称context rot或“增大timeout证明prompt有问题”。后续实际任务的最终回答曾用71.1秒，原45秒配置确实缺少处理这类长输出的裕量；失败调用保留未知用量。
