# 从轨迹到反馈再到更新：跨论文综合

核验日期：2026-09-18。本文综合多路独立阅读及主线程源码复核，讨论反馈机制；没有在本轮运行模型或验证学习收益。SkillEvo、SkillTriage 为论文级证据，未确认官方实现；GEPA 为当日 main/文档，其余已核验源码版本见各阅读稿。

## 1. 先分开三个问题

1. **评价依据从哪里来？** 测试、环境状态、人工处理记录、任务规则或模型判断，来源各异。
2. **怎样据此解释失败、提出修改？** 更新器读取任务与执行证据；LLM 可以归因，但归因文字仍可能出错。
3. **怎样知道修改对以后有帮助？** 需要再次执行以及未参与修改的任务评价；不能用同一次反思的自信替代。

学习时不一定有 gold。ReasoningBank 使用模型代理判断学习，最终效果另由 benchmark 评价。另一方面，SkillSmith 和 Evo-Harness 的一些训练分支拥有答案/rubric；迁移时不能假定这些信息天然存在。

## 2. 逐篇比较真实的数据流

| 工作 | 反馈从哪里来 | 更新/诊断模块实际看什么 | 关键边界 |
| --- | --- | --- | --- |
| [ReasoningBank](https://arxiv.org/html/2509.25140v2) | LLM 对 task + 运行证据判断成功/失败 | SWE 提炼器读任务与非 system 消息，包括已记录命令结果；成功/失败选择不同提炼指令 | 无 gold 也能学习，但标签是 proxy；没有运行过的检查不会自动产生 |
| [Reflexion](https://arxiv.org/html/2303.11366v4) 编程分支 | 真实执行内部测试，返回通过/失败断言、实际输出、异常 | 当前实现 + 测试反馈；下一轮生成器另收到原任务与反思 | 测试预期通常由模型生成，执行真实不保证标准正确；主要改善同题重试 |
| [SkillFlow](https://github.com/ZhangZi-a/SkillFlow/blob/7b49ff5a7e26cd7706e959bfa0dba4746d18440d/libs/skill_evolution/patcher.py) | trial reward、结果文件、CTRF 失败测试/异常 | 当前 Skill 快照 + 任务标识 + 结果 + 精简 ATIF 轨迹 | 有轨迹但有损；所查 compactor 不复制首个 user 消息正文；逐任务 verifier 未全部核验 |
| [Evo-Harness CL](https://github.com/A-EVO-Lab/a-evolve/blob/3c7c7b8c62a3f07da1d4407aa03f0ca079954bcf/evo_harness/cl_bench.py#L1101) | evaluator 的 rubric 满足情况；默认将失败项改写成用户口吻 | Solver 在原会话内提出经验；Curator 后续整理候选与现有库 | 改写反馈不产生新事实；简短 feedback 字段不等于没有原轨迹 |
| [SkillSmith](https://github.com/yangforever17/SkillSmith/blob/2cbbd37c5293c3c06f1f5efc5709382639763cfa/src/skillsmith/loop.py#L374) | scorer 对比答案；附失败诊断，候选再验证 | 任务、gold、预测、分数、trace、现有 Skill/工具及旧失败模式 | 公开 trace 不是完整工具日志；有 gold 的训练条件不能直接等同日常无 gold 会话 |
| [SkillEvo](https://arxiv.org/html/2608.13120v1) | 人工已解决工单生成参考解法；Verifier 对模拟多轮回答评价 | 人工事实 + 模拟对话 + verifier 证据，区分知识缺口、能力限制、评价噪声 | 参考解法不进入模拟用户；主要验证咨询内容，不是生产操作真实生效 |
| [SkillTriage](https://arxiv.org/html/2608.11888v1) | 已确认退化的 target/reference 运行及测试结果 | 同任务要求、实际加载 Skill、两条有序轨迹、产物、时间/token | 从已确认问题做差分诊断；不是任意日志的自动真值生成器，也不直接完成修复 |
| [GEPA](https://github.com/gepa-ai/gepa/blob/main/src/gepa/core/adapter.py) | 接入方 evaluator 提供分数和诊断 | 适配器从输出/轨迹构造 Inputs、Generated Outputs、Feedback 等反思样本 | 引擎不解释轨迹语义；score 用于比较，rich feedback 用于提案；正确性标准仍由接入方负责 |

GRASP 的探针机制及原分支未完成核验的边界另见外部反馈阅读稿，本表不把未复核源码细节当结论。

## 3. 一个解释轨迹价值的真实案例

SkillTriage 的 openpyxl 案例中，任务要求创建仓库内模块。target 安装外部 openpyxl、切换目录并移除仓库导入路径，之后的自检验证了另一个包；verifier 从任务仓库导入而失败。reference 则在仓库内修复兼容问题。

仅有 FAIL，无法区分函数逻辑错、导入环境错或 checker 错。把路径、命令、测试与产物连起来，才形成有依据的环境漂移诊断。论文没有刊出该例全部 Skill 原句，故不能再断言某句话就是唯一根因。[论文案例](https://arxiv.org/html/2608.11888v1#S4.SS2)

这揭示两个不同问题：结果有没有违反任务要求，以及哪个持久组件值得改。前者有测试证据，不代表后者已经被证明。

## 4. 可迁移的最小实现建议

以下是综合推导的设计，不是某篇论文已提供的成品系统。

- **记录执行。** 原始日志不可变保存，统一可取得的消息、工具调用参数/返回值、当前目录、产物差异与 Skill 加载证据。保留缺失/截断标记；只承诺可见数据，不依赖隐藏推理。
- **获取反馈。** 针对明确任务要求运行现有测试或产物检查；收集实际 review；没有这些标准时，允许任务和轨迹驱动的 LLM proxy，但标明其来源和不确定性。
- **绑定版本。** 每个检查绑定检查时的代码/环境。中途一次测试失败、最终修好，不能被汇总成最终失败；一次命令成功也不等于整个任务完成。
- **构造诊断材料。** 输入原任务、相关时间线、实际产物、当前 Skill 和逐项检查；允许读取原日志补证。输出应区分确认违反的要求、引用的事件、原因假设、缺失证据及建议修改对象。
- **产生候选。** 规则错误可改 Skill；重复且适合确定性实现的操作才考虑 helper；工具、环境或评价器有错时，不能一律往 Skill 追加警告。没有 Skill 实际消费证据时，不声称 Skill 导致失败。
- **检查收益。** 适用时从相同初态运行旧/新版本，并检查相关其他任务；真实任务不可完整重放时，保留这个边界。用于选候选的开发 probe 与最终未见任务分开。

LLM 可以承担诊断及修改，但不承担凭空补齐未观测事实的责任。生产阶段的弱反馈与实验阶段的独立效果评价可以并存。

## 5. 一项足以检验主张的消融

在相同模型、任务划分、更新预算和检查器下比较：
A. 分数 + 当前 Skill；
B. 原任务 + 分数 + 轨迹 + 当前 Skill；
C. B 再加逐项测试/产物/review 诊断。

分别记录新任务通过率、同类错误复发、引入的回归，以及采集、诊断、更新、重评和执行的总成本。三组应使用相同可访问反馈权限，最终测试信息不能回流修改。该比较检验详细证据是否带来净收益；在实际运行前不预设 C 更好。
