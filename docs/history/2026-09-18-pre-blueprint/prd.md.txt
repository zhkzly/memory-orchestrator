# Agent 经验学习系统：架构与设计边界

状态：planning。此任务交付可审阅的设计；尚未开始产品实现、模型调用或 benchmark。

## Goal

参考已读论文与源码，形成可接入现成 Agent 的经验学习与 Skill 维护系统实现方案：覆盖经验积累、归因、生成/修订、组合关系、检查、版本选择和发布。用户不要求新算法，也不以复现某一篇论文作为项目目标。2026-09-18 最新纠偏明确：先推进参考实现，不把先导实验验证项目必要性作为开发入口。

## 用户要求与已确定边界

用户希望先把“整体的架构和设计边界做好”，并使用已有 Trellis 命令组织后续工作。前序讨论已明确：
- 第一批消费者是 Codex、Claude Code，核心不绑定某个执行器。
- working memory 和原生工具循环交给执行器。
- 经验积累、首次 Skill 生成、已有 Skill 修订、候选验证和发布需要分开。
- 长会话存在要求变化、任务切换、恢复与延迟反馈。
- 日常任务与 benchmark 使用相同维护核心，但反馈权限和评价协议保留差异。
- 项目结果由实测支持，不用模块数量、结构评分或 Skill 数量代替收益。

## Confirmed Facts

- 当前是 CLI-first TypeScript/MCP 原型，有 Markdown vault、分层上下文、会话标记提取和维护 controller。
- 原生完整轨迹适配、目标版本关联、学习候选库、配对执行验证及跨 Agent 收益尚未实现或验证。
- 文献阅读、源码核验和方法提案已在 docs/references 与 docs/research 归档；没有端到端学习成绩。
- Trellis 0.6.17 已安装；其开发规范是本项目的工程管理资料，不是产品运行时学习库。

## Requirements

- R1：明确模块所有者、读写对象、输入输出及副作用边界。
- R2：定义任务/要求、观测事件、反馈、经验、Skill 版本、候选修改、验证与发布之间的关系。
- R3：区分事实、模型判断、归因假设与执行效果；支持缺失、歧义、取消和延迟反馈。
- R4：统一生成与演化接口，保留结构化原子操作与 NOOP，禁止候选直接成为 active。
- R5：Agent、任务环境、反馈提供者分别适配；不假定能取得隐藏推理或无损完整轨迹。
- R6：说明当前版本、候选版本、历史版本及每次执行的固定快照。
- R7：在实现前保留评测所需的身份、状态、数据划分与全成本信息。
- R8：把当前实现、目标设计、方法假设和实际结果明确分开。
- R9：支持单次经历、同题多次执行、跨题同类经历及反例，避免把偶然成功或重复评审当稳定收益。
- R10：归因结果必须指向具体问题与修改对象，并落实到受限操作；不把所有失败归咎于 Skill。
- R11：区分 Skill 依赖、声明冲突、共用记录和测得影响，并支持相关组合的局部检查。
- R12：区分库版本选择与库内 Skill 选择，默认使用适用配置下已发布的 active 版本。
- R13：先实现完整机制的最小版本，效果评价随后开展；产品内的更新检查和发布不能删除。

逐项来源与注意事项见 [用户关键节点](requirements-ledger.md)。

## 策略实现与后续评价

采样数、证据预算、检索排序、归因提示词、候选数、准入阈值与组合检查深度采用可替换接口和显式运行配置。可先实现参考策略，再用实验比较；不等待先证明最优策略才开发。

真实模型运行前固定任务、可用日志、反馈权限及费用上限；这些限制不阻止确定性核心、版本库、操作接口和本地检查的实现。更新验收是产品功能，benchmark 是评价工具，二者都不是“先证明项目值得做”的立项门槛。
