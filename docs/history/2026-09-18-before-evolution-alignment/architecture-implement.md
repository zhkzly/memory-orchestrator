# 参考实现交付计划

状态：planning。用户已纠正“先验证项目必要性”的推进方向：目标是参考论文和源码，实现完整的经验积累与 Skill 演化系统。更新检查是产品组件；benchmark 是后续评价入口，不作为开始编写核心代码的前置条件。

需求依据：[用户关键节点](requirements-ledger.md)。本文件替代此前以“先导收益成立”为入口的 P0–P4 计划。

宏观节点和不变量以 [总纲摘要](../../../docs/blueprint/context.md) 为准；本文件只细化交付步骤。每个产品实现子任务绑定总纲版本、涉及的 Nxx/Kxx、允许路径与检查点，恢复时读取 resume.md。

v1.1 已补齐 Q01–Q28、节点实现步骤、参考 prompt/schema 和异常分支。实施时直接使用当前节点契约，不再重新发明一套分层架构。每个字段/接口应有当前消费者；关系评分、多候选、微批可用普通函数/循环/任务池实现，不为未来假设预建注册器、策略 DSL 或兼容框架。

## M1：状态、存储与修改接口

- [ ] 定义 Run/Event/GoalRevision/Feedback/Experience/SkillRevision/LibrarySnapshot/PatchProposal 的独立语义。
- [ ] 实现原始证据引用、经验池、不可变候选快照、父版本与 active 指针。
- [ ] 实现 ADD/PATCH/RETIRE/NOOP，检查基础版本、目标范围、引用及依赖。
- [ ] 区分库版本、Skill 修订、任务轮次；候选创建不自动发布。
- [ ] 从既有真实日志/已发布源码工件派生输入例子，覆盖空库、新建、修订、失效基础版本和未知反馈。
- [ ] 验收：同一组输入能形成可追溯的经验/候选记录；未发布候选不会被运行入口采用。

这一步以确定性代码和本地检查完成，不依赖先跑一套 benchmark 或调用模型。

## M2：Agent、任务与反馈接入

- [ ] 定义 Agent Adapter 和能力声明：可见事件、资产提供模式、用量和缺失。
- [ ] 将任务/环境准备、Agent 执行、外部反馈分开；Solver 的公开输入与私有验收材料分开。
- [ ] 执行前持久化 RunGroupPlan；隔离同题多次运行，组闭合再学习；无产物或无标准输出合法 unknown。
- [ ] 接首个原生执行器，建立真实调用/返回配对和产物关联。
- [ ] 实现目标修订、切换、恢复与延迟反馈关联；原始记录不被派生标注覆盖。
- [ ] 验收：取得真实 RunBundle，并明确提供、读取、采用、效果四种不同证据。

## M3：证据整理与经验提炼

- [ ] 实现工具/路径/测试/目标/版本索引和按需读取原文接口。
- [ ] 从反馈选择相关片段，补充原要求、关键操作、环境、后续恢复；超预算或缺失时保留 unknown。
- [ ] EvidencePacket 区分已提供片段与可补读目录；保留字节范围、覆盖/缺失及跨任务绑定。模型输出的 schema 校验与事实支撑检查分开。
- [ ] 实现可替换的提炼器：观察事实、候选经验、证据引用、适用范围和缺失信息。
- [ ] 支持从经验池选择同类经历及反例；保存单例、同题多次执行、跨题比较的来源区别。
- [ ] 验收：提炼结果可回到实际输入，不能把摘要或模型自述当作环境事实。

## M4：归因、Skill 生成与演化

- [ ] 归因输出问题类型、相关事件、候选 Skill/规则、替代解释和拟改变的行为。
- [ ] 分开处理未提供/未选中、内容缺口、组合冲突、工具缺口、环境/评价问题。
- [ ] 当前库为空时生成候选；已有能力时优先对照后决定 PATCH/ADD/NOOP。
- [ ] 同类经验归集后形成局部操作；Skill、引用和必要脚本的耦合变化作为同一候选包。
- [ ] 保存 depends_on、声明的 conflicts_with、观测 co-use 和实际对照结果的区别。
- [ ] 验收：每个操作具有证据、基础版本、适用范围和验证计划；不能一条轨迹机械生成一个 Skill。

## M5：检查、版本选择与发布

- [ ] 实现结构检查及可调用的候选/基线执行检查接口。
- [ ] 复用对显式快照的纯选择函数，验证候选不临时切换 active；验证 lane 禁止学习回调。
- [ ] 支持配置重复执行次数，保留全部通过、失败、异常和未知，避免一次成功覆盖其他结果。
- [ ] 记录质量、回归、稳定性、上下文和全成本；准入规则可配置且在运行前确定。
- [ ] 发布适用配置下的 active 版本，运行开始时固定快照；失败保留旧版，支持回退。
- [ ] 验证绑定准确 candidate/base/config/protocol；发布比较 digest 与 generation，保留事务提交点及崩溃恢复语义。
- [ ] 将“选择库版本”和“为当前任务选择库内 Skill”实现为不同决策。
- [ ] 对实际相关 Skill 组合做保留依赖的局部对照，不枚举所有组合。
- [ ] 验收：过期 base、依赖缺失、失败检查或证据不足不能误发布；执行中的快照不漂移。

## M6：第二执行器、benchmark 与效果报告

- [ ] 接第二个执行器，分别检查接口、资产消费与冻结经验迁移。
- [ ] 复用已有任务环境/评分器接 benchmark，不重写维护核心。
- [ ] 区分在线更新协议与冻结记忆协议，以及开发/回归/最终测试的权限。
- [ ] 记录所有分配槽位与全部执行、提炼、候选、验证、补救成本。
- [ ] 评价/索引/选择调用同样记录用量；按互斥 stage 和 usage_id 求和，失败候选作为切片，禁止重复计费。
- [ ] 报告成功、失败、回归、未知和真实适用范围，不预写提升数字。

M6 用于衡量已经实现的系统，不用于决定是否允许完成 M1–M5。

## 实施管理

每个里程碑建立有具体文件边界和行为验收的实现子任务。产品源码变更前读取现有规范、建立实现契约及必要的验收/mutation 执照；不把这一工程质量流程解释为项目立项验证。当前修订只纠正计划和需求记录，尚未运行 task.py start 或编写产品代码。

已有工程命令为 npm run build 和 npm run harness；没有独立 npm test/lint 脚本。依赖准备、原生模型配置和调用预算按实际运行所需处理，不成为确定性模块实现的无关阻碍。
