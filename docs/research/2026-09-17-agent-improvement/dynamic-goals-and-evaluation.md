# 动态目标会话中的经验提取与评价协议（拟议）

日期：2026-09-18。状态：设计审查与文献核验，没有运行模型、benchmark、人工标注实验或修改产品实现。目标仍是独立解决真实问题，不以论文复现或算法首创为前提。

## 1. 核心单位与责任边界

会话不等于一个任务，一项任务也可能包含多个要求版本。经验提取以“目标身份、要求版本、相关执行片段、被测状态及反馈”为单位。A→B→A 中 A 的证据可以是不连续事件；B 导致的共享文件或环境变化可能是必要依赖。

这是学习入口的旁路标注和索引，不接管原生 Agent 的任务调度或 working memory。原始日志保留，派生标注可版本化修正。

须区分目标修订、独立任务切换、暂停恢复、Agent 对原要求的误解，以及无法判定的澄清。不能把 Agent 自己的新计划当用户新要求，也不能拿最后一次要求追溯评价整段历史。

执行状态（进行中、暂停、取消、结束）与评价结果（pass/fail/unknown）分开。取消不是失败，命令退出 0 也不是整体任务成功。

## 2. 最小记录

- GoalRevision：目标 ID、要求 ID/版本、来源用户事件、适用范围、生效位置、被何次修订替代。
- EventBinding：事件 ID、一个或多个关联目标、原文引用、可取得的产物/环境版本、关联依据及缺失标记。
- Feedback：检查 ID、评价标准、目标/要求版本、被测状态、结果、评价器状态、反馈来源、执行及到达时间。
- ExperienceCandidate：前提、观察事实、候选指导、支持和反例引用、替代解释、缺失信息及适用范围。

延迟反馈按检查 ID/产物版本回填；无法绑定时保持未匹配，不能默认属于当前目标。在线供给只能使用当时已有信息；离线学习可利用后来 review，但记录其到达时间和评价对象，不能把后来新增要求当成原先义务。

## 3. 提取过程

1. 程序解析事件，按调用 ID 配对请求/返回，索引文件、测试、产物与版本。
2. 读取目标及修订记录，不确定的边界保留歧义。
3. 从真实反馈或已验证交付物定位入口。
4. 找相关修改、当时读取的规则、被测环境与后续恢复；关系只是检索线索，不冒充完整因果图。
5. 构造带引用的证据包，必须包含相关要求及修订、判定依据和被测版本。
6. 提炼器可按需请求原事件、diff、早期要求。在预算内仍不足则弃权。
7. 检索其他同类经历和反例，最后生成受限记忆补丁。

原生采集已缺失的内容不能由摘要补造。没有 Skill 读取事件可能表示采集缺失，不能直接断言没有使用。

## 4. 单轨迹与多轨迹

一次经历用于发现局部问题；同题多次执行用于比较路线和采样波动；跨题同类经历用于确定适用边界和寻找反例；旧/新 Skill 的受控执行用于测修改效果。

默认不是固定只学单轨迹，而是先从一例提出假设，再检索支持和反例。明确契约和一次可验证反例可以支持窄范围候选，不凭任意“三次/五次”门槛宣布一般规律。

分开两项对照：
- 固定既有历史池、反馈权限、提炼输入预算及候选验证预算，比较单例和多例组织方式。
- 若多轨迹来自额外采样，把新增执行、筛选、提炼和验证全部计费，与等总预算方案比较。

同题 retry 不计为独立任务，也不能代替跨任务学习收益。

## 5. 是否需要 Skill

- 单次事实或尚不确定的经验：留在情景/项目记忆。
- 已有 Skill 覆盖且新证据支持局部修订：UPDATE。
- 可复用操作流程尚无对应能力入口：提出 CREATE 候选。
- 内容正确但没加载：先查提供/检索问题。
- 可被简单确定性检查直接解决：比较脚本、测试或 hook。
- 无依据、无新增价值、要求已撤销：NOOP。

操作合法只约束修改面，不证明语义正确。发布须同时考虑目标行为、其他任务回归、上下文长度及维护总成本。

## 6. 三个研究问题如何测

| 问题 | 方法假设 | 关键对照与指标 |
| --- | --- | --- |
| 长且目标变化的轨迹能否提供可靠证据 | 要求版本、反馈绑定、按需展开 | 首尾截断；全会话/分块摘要；普通事件检索；拟议方法；人工标注上限。测目标误绑定、事实覆盖、引用支撑、错误确定化、弃权及总成本 |
| 经验是否范围清楚且不会失控增长 | 检索现有资产、限定修改、检索反例、版本验证 | 与直接追加/重写及静态 Skill 比较；测错误触发、重复/过时指导、上下文成本和后续回归 |
| 后续收益能否超过维护开销 | 保留经验证的更新并按任务提供 | 原生 Agent、同历史静态 Skill、适用现成方案、候选系统；计入所有执行、提炼、失败候选、验证与人工补救，不按成功样本筛分母 |

避免完整全因子实验。先在开发集分别确认关键差异，再冻结组合配置做最终评价。结构指标改善不等于任务结果改善。

## 7. 两层证据，而非一个万能 benchmark

**公开机制验证：SkillFlow。** 166 任务、20 个工作流族，族内固定顺序，从空 Skill 开始跨任务更新，跨族清空；支持原生 CLI。主要是办公/数据工作流，不能据此声称已证明软件仓库维护或会话内目标变化。官方在线协议是先测当前题，再将反馈用于后题。

保留官方顺序与清库边界；开发族/最终评价族划分、候选回归门和顺序扰动均须标为本项目扩展协议，不能混成官方成绩。最终序列不得提前读取后续答案；候选验证仅用可访问的已发生任务或开发材料。本轮仍未核验独立数据集中的逐任务 verifier。

来源：https://arxiv.org/html/2604.17308v1#S2.SS4
接口：https://github.com/ZhangZi-a/SkillFlow

**真实部署问题：本地动态目标会话审计。** 先小规模选真实发生过修订、切换、恢复、纠正、延迟反馈和缺失日志的会话，按整个会话划分开发/审计集。人工只标可核查要求、事件归属、反馈状态和可接受证据，不假定有唯一根因 gold。保留歧义；审阅尽量对方法身份盲化，有独立审阅时记录分歧。没有独立审阅则披露这一限制。

同时报告固定目标与变化目标子集。进行受控移除关键返回/修订事件的缺失实验，但不冒称其等同自然缺失分布。若只有人工正确标注上限组有效，说明自动标注仍是瓶颈；若普通检索同效更便宜，应简化系统。

后续可用冻结记忆在 SkillsBench 做补充验证，但 SkillFlow 使用过 18 个 SkillsBench seed，须检查派生/任务重叠，未去重不能宣称独立外推。SkillsBench 论文旧快照与 v1.1 发布数量不同，实验须固定版本和分母。

## 8. 当前最强反对意见

目标版本与事件关联自身可能提取错；证据检索可能只找支持原假设的片段；多轨迹可能只是重复同一种错误。新增复杂度是否值得，必须由上述简单对照、独立证据审计和后续任务结果共同回答。目前没有已测收益可报告。
