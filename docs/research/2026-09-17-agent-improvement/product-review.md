# 产品质疑：现成编程 Agent 使用者是否需要另一个 Memory Orchestrator

评审日期：2026-09-17 至 2026-09-18。源码基线：`984ce57fbbc50182b1270d59e6eb1648ad43dbe4`；所审产品文件无未提交修改。只读检查 README、`src/mcp.ts`、`src/core.ts`、`src/controller.ts`，为核对检索计数追到 `src/store.ts`。未运行模型、测试、真实 vault 或全局配置。未读取其他评审文件。

**结论：当前“通用记忆 + 自我演化控制器”产品方向 NO-GO；只对一个具体用户问题做小规模验证，暂不开发新框架。** 对功能重叠的判断置信度高；对市场需求的判断置信度低，因为当前证据没有真实用户访谈、返工账本或对照执行。

这里的 NO-GO 不表示代码没有工程价值。它表示还不能把“用户为什么需要它、现有办法为什么不够、自己的方法解决了什么”连成已经成立的项目叙事。当前实现缺少某能力，也不等于市场缺少该能力。

## 3. 只保留一个待证问题：从真实返工到有效改动的成本

**用户原话应当能够是：我在同一个仓库反复让 Codex/Claude 做一类工作；它又犯了我纠正过的问题。我不知道该改哪份指令，也不想为验证一条改动先搭一套基准。**

这是假设，不是访谈结论。它针对的是已有可重复工作、能判断产物对错、已经用过原生规则/Skill 的开发者或小团队维护者；不适合所有聊天用户、一次性开放任务或没有可验证结果的“整体变聪明”。

触发时刻是第二次可辨认的同类返工，或一次原本有效的本地流程在环境改变后失效。例如某个仓库的同类变更反复漏掉维护者要求的配套产物。示例仅说明消费时刻，不代表已观察到真实事故。

实际待解决的工作只有三个：保留足够复现当时失败的状态；确定最小可控改动；用原任务及新出现的相近任务判断改动是否值得保留。AGENTS.md、原生记忆、Skill、hook 都可能是正确结果。不能预设每次必须产生记忆，也不能预设每次必须优化 Skill。

**潜在工程价值只能来自减少这个具体用户的准备、定位和维护成本。** evaluator、held-out probe、回归准入不是本项目的新方法；GEPA/GRASP 可以直接充当既有工具。如果最后仅产出一个短 Skill 和一个项目脚本，就按这个粒度交付。

这个问题为什么可能仍值得问：现成方法的输入通常要求可执行任务与可判断结果，而日常返工最初是混在会话、工作区和人工审查里的事件。把输入准备好可能有成本。但是“可能有成本”只是机制推断；没有计时与用户样本，不能把它升格为明确 gap。

最有力的反证也很简单：维护者十几分钟就能指出原因、写好规则并从后续工作中验证，或者原生 skill-creator / GEPA Skill 已能完成。若如此，不应另建产品。

不再提出第二条独立产品线。跨工具记忆同步、记忆清理、定时反思、Skill 版本准入都已有便宜替代或明确方法先例；在没有真实事故之前把它们捆绑起来，只会增加框架层数。

| 追问 | 可接受的证据；当前是否具有 |
| --- | --- |
| “谁现在会用？不用会损失什么？” | 具体使用者的真实返工记录、原始请求、产物差异、纠正动作和花费时间。当前没有，不能用“Agent 普遍会忘”回答。 |
| “你为什么不能直接给我写 20 行 Skill？” | 相同信息、相近人工预算下的最佳手工规则/Skill/hook 基线；报告额外收益和总维护成本。若效果相同且手工更省事，就承认无需产品。 |
| “这不是 OpenViking 的轻量重写吗？” | 证明用户需要的是某个已发生的返工处理结果，且存储/召回替换并不提供同等结果；实际以 OpenViking 作为存储也能消费该功能。否则当前重叠质疑成立。 |

| “同一个模型再试一次也可能成功，为什么归功于你的改动？” | 固定 Agent/模型/工具版本与环境、隔离会话和原生记忆污染、配对重复；把重复尝试成本算给两边。当前的 retrieval_count 与 rubric 分数不能回答。 |

| “增加一条规则后，怎么知道下个月仍然适用？” | 报告冻结配置和适用范围，保存来源及实际后续结果；环境变化触发重新核查。文件 hash 变化只能提示重查，不等于语义失效；“未观测回归”也不是保证零回归。 |
| “为什么现在需要 1,400 行 controller？” | 逐条映射到用户实际执行的必要步骤。当前更多是维护报告能力，不能拿代码量、命令数和内部结构评分证明产品必要性。 |

## 5. 最小真实用户验证：先证明不能被便宜办法替代

以下是提议的验证协议，尚未执行；人数、时间和任务数都是设计值，不是观测结果。当前只读授权下不发起招募、不运行模型、不改用户配置。

1. **找两位真实使用者，各选一种经常出现的仓库任务。** 不要求同时使用 Codex 和 Claude；先证明单一工具场景有价值，再谈跨工具。每人提供两次可核对的同类返工记录，保留没有提供足够证据的失败招募，不用回忆概述补齐。
2. **现场做一次便宜替代。** 使用者与评审者直接看原始材料，用原生指令、手工 Skill、测试或 hook 修复；预先约定约 30 分钟的初次处理预算，记录实际耗时与剩余步骤。该预算是验证设计，不是给所有用户规定 SLA。原生机制已解决则停止扩建。
3. **仍未解决时，直接试现有方案。** 按问题类型选择 OpenViking、GEPA Skill 或 GRASP，不机械地全装一遍。记录准备可执行输入、提供验收、接入及维护所花的时间。不能把本项目自动化时间与竞品从零开发时间不对称比较。
4. **观察后续自然发生的任务。** 每人至少记录三次相近任务：是否再次返工、人工纠正分钟数、额外模型/运行成本、旧任务是否回归、是否需要维护规则。样本少时只报告逐例结果，不宣布普遍成功率或跨仓库泛化。
5. **最后才决定是否写产品代码。** 只有两位使用者都遇到相同且重复的剩余手工步骤、现有办法未以可接受成本解决、并愿意继续在自己的工作中使用这一步，才实现那一个步骤。优先是脚本或原生 Skill，之后再看是否需要独立 CLI。

明确停止条件：找不到可复现的同类返工；大部分问题由原生规则/测试直接解决；未来任务不再重复；准备验收的时间超过节省的返工时间；用户必须持续维护第二套真相；或仅有原项目作者愿意使用。命中这些情况，不应通过扩展用户群或增加功能来保住立项。

若验证通过，可成立的项目叙事是：“在某类真实仓库任务上，发现维护者从一次 Agent 返工到有效本地修正需要若干具体手工步骤；复用原生扩展和已有优化方法，减少这些步骤，并用真实后续任务报告收益与回归。”在这之前，最诚实的成果是一次否定过宽方向、明确下一步验证的产品审查。

## 6. 第二轮收窄：已有多 Skill 库的诊断与维护

**研究原创性仍为 NO-GO。** SkillEvo 已将失败按 Knowledge Gap、Capability Limit、Evaluation Noise 区分，只有前一类进入修改反馈；因此“先归因再修改”也不能构成新意。它还检查事实和结构退化。这里按论文方法事实引用，不把论文实验效果外推到 Codex 用户。[SkillEvo 原文 §3.2–3.3](https://arxiv.org/html/2608.13120v1)。

SkillSV 又已覆盖结构有效的反事实、paired deletion、length-neutral padding、受 rollout 预算约束的价值估计及安全裁剪。因此连“考虑结构和上下文成本，在预算内估计应删除哪条”也不能直接当原创点。其问题定义是固定 Skill 内部单元的价值，不能自动证明已经交付现成 Agent 的跨 Skill 库诊断；但这一区别只允许继续验证产品操作成本，不足以声称新的研究空白。[SkillSV 论文摘要](https://arxiv.org/abs/2608.04562v1)。

**系统产品价值只能作为上一问题的一个更窄场景验证：用户已有 Skill 库，组合或更新后出现异常，想以可接受成本找出应停用或修订的最小部分，同时保留其他工作流。** 这不是第二套记忆产品，也不预设要实现新优化器。适用人群缩到维护共享 Skill 包的小团队维护者或重度用户；不能继续泛称“所有 Codex/Claude 使用者”。

必须存在真实触发事件：此前流程可用，一次明确的 Skill 变更后发生可复现的停顿、错误权限判断或操作偏航；维护者需要保留库内其他能力，不能简单回退整个版本。这里尚未拿到任何这样的第一手案例。Skill 安装很多不等于单次运行加载很多，不能把安装数量当问题规模；Codex 已采用元信息先加载、正文按需加载的机制。[OpenAI Docs：Skills](https://developers.openai.com/codex/skills)。

需要先击败的便宜替代：

| 替代 | 它何时已经足够 | 剩余需求必须用什么证明 |
| --- | --- | --- |
| 直接追问并检索原文 | 模型指出冲突或多余审批来自哪条 Skill，维护者改一行即可。OpenAI 官方已经建议要求模型给出引发暂停/偏航的确切 Skill 文件和原文。 | 真实案例中该步骤无法定位或给出错误归因，且有执行反证。不能只以“模型自述不够科学”为由拒绝这条便宜路径。[OpenAI 官方模型指南：Instruction following](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)。 |
| 回退最近改动 | 异常紧随某次安装/更新出现，回退后用户任务恢复，用户能接受该取舍。 | 用户确实需要新版中其他能力，或多个独立改动使回退成本不可接受。不能为了展示诊断器而拒绝一次回退。 |
| 手工逐条禁用 | 实际候选数很小，任务容易重复，执行成本低；现成开关与脚本足够。 | 记录实际候选数、重跑次数、时间和费用，而非引用“组合空间指数爆炸”替代实际工作量。删除造成的上下文变化和运行噪声都应记录，但它们不是自动立项理由。 |
| GEPA / 既有诊断或裁剪方法 | 把配置选择作为优化对象，用现有 evaluator 比较，已经能给出可用结果。 | 同预算直接使用的接入账本；只有公共、重复的手工接线工作才可能值得封装。算法能否处理与产品是否开箱可用是两项不同证据。 |
| 整体库准入/回退 gate | 用户只要“不让坏更新上线”，接受拒绝候选或保留旧版。 | 证明用户的目标是保留新版部分收益，且拒绝整个候选确有损失。不能把定位粒度更细本身当用户收益。 |

最强面试追问应改成：**“拿一位真实用户的一次事故给我看：为什么直接问模型、回退最近 Skill、逐条禁用还不够？你的工具究竟替他省下了哪一步，省了多少，包括验证工具自己结论的时间？”**

值得进入实现前，至少要取得这些一手材料：两位非作者用户的真实事故包；事故时的 Agent/模型/工具版本、实际 Skill 及指令来源、改动前后文件、任务输入与可核对结果；维护者执行便宜替代的过程和计时；原配置与候选修复的重复执行结果；后续不同任务上仍需要保留哪些能力；用户主动再次使用诊断流程的记录。无法复现的案例也保留，不用人工设计冲突样例代替需求证据。

第一版验证完全可以是人工服务：帮助两位用户完成各一次真实事故诊断，把每个操作写成清单。只有两次出现同一段费时、可自动化且现有工具未方便覆盖的步骤，才写一个局部脚本或 CLI。验收是恢复用户工作、减少其主动诊断/维护时间和错误修复，成本要包含所有重跑及审核；不按找出多少冲突、记忆条数或内部评分验收。

**最终立项判断不变：现在不扩建通用 Memory Orchestrator，不宣称演化/归因/防回归算法创新。建议先收集上述产品证据；没有证据就停止。** 若证据成立，可以诚实定位为面向现成 Agent 使用者的可复现配置诊断工具，复用既有算法和原生工件。它是否仍需要叫“Memory Orchestrator”，应由实际消费对象决定。

## 7. 用户澄清后的工程项目评审

**结论调整为条件性 GO：值得做一个仓库、一类任务、一个现成 Agent 的工程试点，同时收集真实使用证据。** 用户明确要求独立解决真实问题、论证和实验扎实，并不要求发明新算法。以前文的研究新颖性不足否决工程项目，不适用于这项标准；“实现前必须已经取得两位外部用户事故”也不作为本轮开工条件。前文源码能力边界与替代基线仍有效，效果主张仍须等待实际证据。

本轮评审对象是：**把仓库维护者在真实任务中的有效纠正，整理为有来源、有版本的项目 Skill，并检查它在后续同类任务中是否减少人工纠正。** 需要验证的部署假设是，纠正材料、适用范围和后续验收目前仍反复需要人工准备，薄工具能够降低这部分成本。这里不声称该痛点已被观察、频繁发生或已有市场规模；试点本身就是取得这些证据的方式。

方法可按候选方案复用 Evo-Harness 做经验整理、借鉴 GRASP 做候选验收，OpenViking 可承担存储。项目贡献应落在真实轨迹和反馈的接入、仓库级适用范围、原生 Skill 交付、后续任务验证及操作成本上。采用已有方法与工程项目成立并不冲突，也无须为了差异化再造数据库、Agent 主循环或通用优化器。

### 具体使用者与首次工作流

首批使用者建议选**维护一个已有测试和代码审查习惯的业务服务，并持续用 Codex 或 Claude Code 完成同类修改的开发者**；可以先由作者自己的真实仓库开始。人负责确认需求和审查纠正是否成立，现成 Agent 负责消费项目 Skill。零基础使用者、一次性探索任务、没有可判断产物的开放任务、纯粹想跨仓库同步偏好的人，不是首轮对象。

首次只选一种工作流：**在同一个服务中新增或修改已有业务 API 的字段、状态或错误分支，并完成相关验证与 review。** 从使用者真实待办中取任务，不为展示效果另造一批错误。选择它的理由是任务边界可冻结、代码和测试可回放、review 能指出具体缺漏，并可能形成“请求解析—业务处理—持久化或外部调用—响应”的可复用检查步骤；这些是选择试点的工程理由，不是已证明会产生收益。

期望保存的是带条件的操作经验，例如：改动涉及某类状态时应追踪哪些读写路径、怎样确认一个现有测试确实覆盖变更、哪个已有用例代表该仓库的约定。不能把某次提交的最终代码或特定答案当通用 Skill。上述示例也不是已发生的用户事故；只有轨迹和维护者确认的反馈真正支持时才写入。

不建议第一轮同时做新特性、故障排查、依赖升级、文档写作与多 Agent 迁移。先使用已经能获得完整轨迹的一种 Agent；第二种 Agent 和第二个仓库是后续外推检验，不是首轮功能清单。如果真实仓库近期没有重复的 API 变更，就不强行造样本：先缩小到它已有的另一类重复维护任务，并在实验前固定类别。

一次真实使用应当能够完整走完：维护者完成任务纠正 → 工具提取有依据的条件与步骤 → 维护者查看 Skill 差异和来源 → 候选在冻结的任务上接受验证 → 通过后由原生 Agent 加载 → 下一次真实任务记录是否还需同类纠正。整理后的文本只是中间产物，后续使用才是消费终点。

### 什么时候便宜办法已经足够

| 情况 | 首选处理 | 对试点的含义 |
| --- | --- | --- |
| 稳定、全仓通用的约定，例如正确的测试命令或代码目录 | 写入简短 AGENTS.md / CLAUDE.md | 不需要反复提取和演化。试点可以识别并建议归位，不能把每条约定都变成新 Skill。 |
| 可机械检查的不变量，例如格式、必需字段、生成文件是否同步、明确禁止的命令 | 测试、静态检查或 hook | Skill 可以教 Agent 怎样满足约束，但不能取代确定性检查；把已有检查漏配当作学习需求会高估产品收益。 |
| 一次整理后已稳定的多步骤流程 | 维护者手工写一份 Skill | 必须作为强基线。自动生成文字质量相近，只能说明生成可行；只有准备、验证或后续维护成本减少才支持继续开发。 |
| 纠正只在这次任务或这个尚未确认的需求下成立 | 保留在任务记录中 | 不提升为仓库经验。缺少泛化依据时允许不产出 Skill。 |
| 多次同类任务需要相似但有条件的路径判断，纠正材料分散且有后续可核对任务 | 试点整理、验证、交付流程 | 这是待验证的适用区间。若静态规则或手工 Skill 已解决，就把交付停在那一层。 |

最需要回答的面试追问是：**“为什么这个仓库值得持续维护经验，而不是把审查者说的话写一次 AGENTS.md？把最好的手工 Skill 摆在旁边后，你还省掉了哪些重复操作？”** 可以通过试点回答它，不必在开始实现前假装已经有结论。

### 三条必要验收

1. **闭环真实、来源可核对，原生 Agent 确实消费产物。** 至少完成一次真实任务纠正到后续新会话加载项目 Skill 的全流程；每条新增经验能追到具体轨迹、对应代码状态、测试结果或已确认的 review 反馈，并标明适用任务与版本。测试失败、用户纠正、模型自我反思须分别记录，不能都折算成“已验证”。候选可以被拒绝或暂存，不为完成流程而强行准入；撤回后要能恢复上个版本并确认新会话实际加载的内容。当前 verifyCandidate 数证据条数、retrieval_count 和内部 rubric 分数不满足这一验收。

2. **在未用于整理经验的同类任务上，比强基线减少纠正且保住任务质量。** 首轮至少比较现有原生配置，以及使用同一批纠正材料、合理人工预算制作的手工 Skill；候选流程与两者使用相同的测试/hook。按独立任务分离整理材料和后续验收材料，不能把同一任务的多次轨迹当新任务；固定 Agent/模型、工具、原生记忆状态和任务起点，必要时配对重复。主指标是维护者的纠正分钟数和轮数，同时报告最终产物验收、原来正确任务的回归、运行费用及延迟，给出全部分母和失败。开始实验前约定值得继续维护的最低净收益与可接受回归界限；小样本只能得出试点结论，不宣称跨仓库泛化。如果只胜过没有规则的弱基线，或者只是把同一任务答案记住，这条不通过。

3. **第二次更新仍减少总维护工作，收益不靠作者在后台手工完成。** 在首版之后再经历一次新的真实纠正或来源变更，复用相同流程完成候选差异、适用范围、验收与版本处理；记录人员实际做了哪些步骤。总账包含首次接入、反馈整理、验收材料准备、审阅 Skill、处理错误建议、运行等待与后续维护，并区分固定成本和每次发生的成本。允许人工确认业务事实，但不能每次仍由作者手工重写 Skill、重建全部实验再称自动化完成。来源 hash 变化只能触发核查，不能直接证明经验错误；没有净节省或使用者不再愿意采用，就停止扩大范围。可保留已经有用的 Skill 或脚本，不必继续扩建控制器。

**建议范围：可以开始这一薄工程试点，边实现边验证上述部署假设；不建议现在建设通用自演化平台。** 有价值的最终证据可以是“在这个仓库的这类任务中，复用已有方法把某些重复人工步骤自动化，减少了多少纠正和维护，付出了多少成本，还在哪些任务上失败”。这已经能够构成扎实的工程项目，无须追加算法首创主张。
