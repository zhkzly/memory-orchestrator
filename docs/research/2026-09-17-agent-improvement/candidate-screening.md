上述“已有”只指论文/源码明确描述了机制，不意味着本轮复现了作者效果，更不意味着这些方法已经解决所有用户场景。

## 一个尚未成立的产品问题

使用者假设：维护一组项目 Skill 的开发者或小团队。触发假设：一次 Skill 变更/组合后，原生 Coding Agent 出现可复现的返工，而且直接问模型、回退最近改动或逐条禁用不能以可接受成本恢复需要的能力。

待验证的问题是：从真实事故构造可复现诊断输入、使用现有方法并核验结果，是否存在重复且昂贵的手工步骤？当前没有足够第一手材料证明它存在，因此不称为已经成立的市场或研究 gap。

如成立，贡献可以是系统与实证：减少准备、诊断和维护成本，复用已知估值/优化方法；不能声称发明 Skill 演化、因果归因或回归准入。

## 停止继续“拼 gap”

不因一个机制被已有工作覆盖，就不断增加“跨 Agent、在线、动态、稀疏”等限定来保护选题。新的限定必须来自真实使用条件，且能产生新的可判别结果。

当前方法原创性判断：NO-GO。当前产品必要性判断：证据不足。允许讨论问题验证；不据此扩建代码。

## 最小判别顺序

1. 先取得可复现的真实事故和当时配置，包含无法复现的失败样本。
2. 同信息条件下先使用原生诊断/手工规则/回退/逐项禁用；记录完整时间和重跑成本。
3. 若仍有重复负担，再试 SkillSV/GEPA/GRASP 等适用现成方法，区分算法问题与接线成本。
4. 只有剩余步骤在不同事故中重复发生，并能改善后续真实工作，才设计最小自动化。

研究评价不能只看诊断命中：应包括恢复任务、保留其他能力、人工耗时、全部模型/重跑成本和后续回归。随机干预 Skill 可见性时先报告分配的意向处理效应；读取/遵循是干预后行为，不能据此筛选样本再宣称因果。

用户已明确目标：独立解决真实问题，论证和实验扎实，不要求发明新算法。因此此台账继续约束原创性表述，但不因模块已有就否决工程项目。最新条件性试点见 project-proposal.md。
