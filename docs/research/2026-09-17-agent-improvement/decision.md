## 1. 裁决

用户要求的是问题驱动、从动机到方法再到证据连贯的项目。此前“先复现 SkillFlow”的建议只解决实现参考，没有建立独立项目动机；不再把它作为产品立项依据。

目前的明确结论：**不以“通用记忆 + Skill 演化”立新方法，也不立即扩建当前实现。** 已有方法足以反驳多个宽泛新意；真实用户中尚未发现本项目能独立解决、且现有简单办法不能解决的重复障碍。

这不意味着必须发明新算法才配做项目。独立系统项目可以复用已有算法，通过真实问题、具体设计选择、可靠交付和对照结果形成贡献。投稿级方法/评测贡献需要额外的最近邻增量；目前没有证据承诺这种增量。用户随后已选择独立真实工程项目，不要求发明新算法；三位审查员补充复审后允许条件性试点，详见最新提案。

## 3. 背景应建立在哪些事实上

现成 Coding Agent 已通过原生指令、Skill、记忆和工具扩展工作流程。外部指导可以持久化并影响后续任务，但新增内容不保证改善表现；先前研究已观察到退化、噪声反馈和成本不划算的条件。

| 已知工作 | 已经覆盖的机制 | 不能再作为独立 gap 的说法 |
| --- | --- | --- |
| [SkillFlow](https://arxiv.org/html/2604.17308v1) | 现成 CLI、跨任务 Skill patch、正负效果评测 | 让现成 Agent 通过经验更新技能 |
| [GRASP](https://arxiv.org/html/2605.29668v1) | 更新前后 probe、硬回归预算、对比修订 | 给更新加回归门 |
| [SkillEvo](https://arxiv.org/html/2608.13120v1) | 区分知识缺口、能力限制和评测噪声 | 先确定失败归因再写经验 |
| [SkillSV](https://arxiv.org/html/2608.04562v1) | 结构有效的反事实、预算受限估值 | 便宜地识别有害 Skill 内容 |
| [SkillTriage](https://arxiv.org/html/2608.11888v1) | Skill 退化案例的成对诊断和归因 | 首次为技能事故提供诊断 |
| [OpenViking 源码](https://github.com/volcengine/OpenViking/blob/20ec78a149a0889a85b038627dddc70b46dceae3/openviking/session/compressor_v3.py#L794) | 受配置控制的技能提炼与更新连接 | OpenViking 只管存储，本项目才会演化 |

实现路径存在不代表默认启用或实际效果已经被本轮验证。对某个竞品的功能差异，也不能代替整个研究领域的最近邻比较。

## 4. 可暂留的完整问题链，但 Gap 尚未成立

以下是**待证的产品假设**，不是把被否决的方法重新命名。

**使用者与触发场景**：维护一组项目 Skill 的开发者或小团队，在组合/升级后遇到重复返工；希望恢复工作并保留其他能力。

**真实需求候选**：从一次混杂在日志、工作区和人工审查中的事故，低成本得到可重现的问题、可核验的诊断和可用的修正。

**候选工程缺口**：现有方法需要的冻结任务、正确结果和可重放环境，在真实事故中可能准备困难。必须用实际操作与计时证明，这些输入准备与维护步骤仍然是瓶颈；不能只因为本仓库没有就声称业界没有。

**研究问题**：对于确有此瓶颈的工作流，自动化这段输入准备和复验流程，能否降低到恢复为止的人工时间与总成本，同时不增加错误修复和后续回归？

**方法地位**：此时不固定新优化器。先用普通 runner、快照、原生诊断和已有估值/优化方法完成事故处理。只有重复步骤被实际确认后，才把那一段做成最小系统。算法复用的来源、适配的部分和个人实现范围需分开说明。

**可能贡献**：若证据支持，可以是事故数据与可复现协议、面向原生 Agent 的系统实现、或明确的成本/适用边界发现。当前不能预写“提升 X%”“普遍避免负迁移”“首次因果演化”。

## 5. 一项可否决立项的先导实验

设计值：2 个自然发生的疑似 Skill 回归事故，加 1 个真实但未退化的更新作为阴性对照。不能植入坏规则后把它说成用户实际需求。

每例对比：当前库、上一个可用库、当前库撤销被怀疑改动；每臂两次新状态执行，总计 3 × 3 × 2 = **18 个结果槽**。这是 3 个案例，不是 18 个独立任务；仅适合判断明显问题与复现成本，不足以证明普遍效果。

固定任务、仓库、模型/CLI、工具权限和执行预算，交错运行；保存首次结果、异常与全部费用。复现不了时先记录不确定性，不继续宣称 Skill 因果责任。读取 Skill 是消费线索，不是有效性标签。

先让熟悉工作流的人使用原生诊断、日志检索和回退完成处理，记录其实际耗时。若这一便宜路径已经解决，保留脚本或短规则即可。若仍有明确剩余负担，再比较 SkillTriage/SkillSV/GEPA 等合适的现成方法，使用同信息、同预算，不能故意弱化基线。

诊断阶段的同题重跑只计成本，不计学习收益。未来若提出改进系统，最终收益必须在未参与设计的后续任务与过去正常任务上测量，分别报告救回、回归、无改善与未判定。

## 6. 否决条件

- 没有可核对的重复事故，或者事故主要来自普通环境/接口故障。
- 原生提示、短清单、测试/hook 或回退已经用较低成本解决。
- 现成方法最小适配即可同效同价。
- 新系统需要比节省的返工更多的输入整理、评测或维护。
- 只有合成故障、同题重试、隐藏答案或被筛掉的异常才能产生漂亮结果。

这些结果分别否决需求、系统必要性、方法增量或效果主张。结果不确定时写“证据不足”，不能用不显著差异证明等价，也不能继续追加条件来保护项目。

## 7. 面试中的可防守表述

现在能说：做了立项审查，识别当前系统的证据缺口和直接最近邻，否决了几个重复方向，设计了可裁决的用户验证。

将来只有验证通过后才能说：在某类真实工作流中发现了具体瓶颈，采用并适配哪些已有方法，独立实现了哪些必要部分，通过什么对照减少了多少工作量，在哪些条件仍然失败。

遇到“别人已经做过”时，应准确承认复用的机制，指出自己经过对照支持的增量；没有增量证据就收缩主张。不能靠给方法起名、增加模块数量或三个 Agent 赞同来防守。
