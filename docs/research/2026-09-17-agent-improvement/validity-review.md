# Coding Agent 经验改进项目：研究有效性审查

审查日期：2026-09-17 至 2026-09-18。范围：一手论文与冻结提交的只读核验；未运行模型、未改产品或配置、未读取其他审查稿、未向外部存储发送私人分析。文中的实验均为待执行设计。

**结论：当前没有形成足以支持新研究方法立项的窄 gap。** 对此判断置信度高；对“该用户的真实工作流是否值得做一个工程系统”尚无执行证据。技能更新、反馈归因、回归门、预算受限的反事实价值估计，均已有直接近邻。把这些组件接到 Codex／Claude Code，可以成为有用的系统贡献，但不能仅凭接入对象不同就宣称方法创新。

本审查只保留 **1 个值得先做的判别问题**：在一个有真实重复失败记录的 Coding Agent 工作流中，自动维护的跨任务经验，能否在完整成本相同的条件下，胜过固定短清单与现成强方法？它首先是部署价值问题；正结果也不会自动产生新颖性。

## 2. 最容易伪装成“Agent 变强”的现象

| 假象 | 替代解释 | 最小识别办法 |
| --- | --- | --- |
| 更新后成功率提高 | 多了反思、judge、探针、重试、更多 actor 思考 | 总系统成本入账；让最简单基线把同等预算用于 actor；报告成功率－成本曲线。 |
| 越做后面的题越好 | 后题更容易、同模板实例重复、故意按可迁移程度排序 | 同题配对且两臂同顺序；按仓库／家族分块；多个冻结顺序。不能把时间趋势当学习效应。 |
| 从失败里学到了规则 | 编辑器读到了隐藏验收细节、gold patch、未来任务描述 | 隔离任务公开证据、开发反馈、最终 test 评分；记录每条更新的输入来源及时间。 |
| 使用率很高 | 只读了 SKILL.md；读后忽略；重复读同一文件 | 分开记录可用、暴露、规则对应动作、最终 outcome；随机暴露的主估计按 assignment 统计。 |
| “使用技能”的任务更成功 | Agent 只在熟悉／容易题调用它 | 不比较自选使用组与未使用组的裸均值；同题随机可用性对照，或直接报告整体策略效应。 |
| 一次技能验证通过 | 技能失败后，原生 agent 靠额外操作补救成功 | 标记技能相关的第一个动作与错误，统计恢复开销；episode success 与 skill success 分开。 |
| 新库比旧库强 | provider 模型快照、CLI、系统指令、MCP、权限或上下文管理同时变化 | 冻结完整 executor tuple；旧／新库在同时间窗口交错执行。 |
| 修好了一类问题 | 对同一题反复试到成功，或题面换实体但答案程序相同 | 首次提交的任务分数不可覆写；训练／开发重跑只算成本；最终 test 为未见问题和变体。 |
| 回归越来越少 | 反复挑同一个 validation，或删除了失败／timeout 记录 | 最终 test 封存；保留所有分配的任务、null、超时、拒绝更新与异常；不只展示 accepted updates。 |
| 技能更短且更快 | 真正效果来自减少上下文、缓存命中或更少检索 | 固定短清单、等长度替换、独立成本账单；内容收益和长度收益分开。 |
| 已能跨模型迁移 | writer 更强、executor 不同、反馈更多 | writer 与 consumer 分开固定；相同 artifact digest 交给第二个 executor；结果按栈报告。 |
| 一条规则被证实有害 | 删除破坏了依赖；共同激活的另一条规则才有问题 | 有效反事实与交互检查；采用 SkillSV 类对照，不能用断链删除制造“贡献”。 |
| 更新策略擅长抗噪声 | 人工噪声独立均匀，但生产误判与困难任务或方法输出相关 | 分开自然噪声、随机翻转、相关噪声；隐藏真实标签仅供评价，不能交给选择策略。 |

以上是实验风险清单，**不是认定上述论文均犯了这些错误**。

## 3. 什么因果对象确实可识别

固定消费者栈 E、任务／环境快照 x、技能库 S 与预算 B，可以识别：

`Δ_system(B) = E[Y(x, E, memory_policy, B) − Y(x, E, simplest_policy, B)]`

这是“部署一个外部经验策略”的总体效果，包含检索、提示长度、维护成本与 actor 适应，最接近用户价值。随机化单位是完整任务副本或无串扰的任务流，不是事后选择的“真正读过技能的成功任务”。

若单独干预某条技能 v 的可用性，可估计 `E[Y | do(v available)] − E[Y | do(v unavailable)]`。这是**可用性意向处理效果**。它不等于“若 agent 真正遵从 v 会怎样”，因为是否遵从受能力和任务难度影响；按实际使用过滤会破坏随机化。

重要边界：随机化只能识别对测量结果的影响。若 Y 只是会系统误判的 self-judge，得到的是对代理分数的因果效应，不能自动升级为真实任务成功的因果效应。需要独立的最终验收；不能让该验收提前给更新器答案。

“技能值低”“错误更新少”“有害条目识别准”可作为机制指标；研究主结果仍应是未来任务的首次成功、回归与完整成本。若只有离线 attribution 指标改善，不能声称现成 Coding Agent 已变强。

## 4. 目前只值得先验证的一个窄问题

**问题：针对一个有真实重复错误的仓库维护工作流，自动更新的程序性经验在固定完整预算下，是否改善未见后续任务的首次成功，且超过同证据构成的固定短清单？**

这是立项前的需求与净效益测试。它没有预先假定某种新“记忆控制器”成立，也不把已知方法的局部复现当创新。

### 4.1 进入实验的前置证据

先从已有历史中冻结一个工作流，例如同一类测试定位／迁移／构建维护；不要混装任意 coding task。至少找出若干**跨不同 issue 重复出现**的可操作错误，并回到原轨迹确认：

1. 当时环境与公开任务信息允许正确操作。
2. 错误不是权限、故障 endpoint、能力完全不足或最终 evaluator 问题。
3. 后续任务确实可能复用相关程序，而不是再次做同一题。
4. 当前原生 agent 已有的指令／技能／记忆没有解决它。

若找不到这个事实基础，停止搭系统。SkillFlow 负例只能证明“技能可能有害”，不能证明该用户存在足以维护一套系统的痛点。

### 4.2 四个必须有的比较对象

| 臂 | 定义与必要性 |
| --- | --- |
| A：最简单替代 | 固定现有原生 agent；省下的维护预算用于正常执行。不得人为压低其可用思考／交互上限。 |
| B：固定短清单 | 从同一批开发历史写出一页有明确适用范围的检查清单；部署后不更新。对有 CI 的流程，采用最简单的“等终态再记录，并附 task／commit 标识”。所有制作成本入账。 |
| C：强现成方法 | 根据工作流选定 Evo-Harness／ReasoningBank 的经验编译方式，加上适用的 GRASP 回归选择；如果声称低成本 attribution／压缩，再必须加入 SkillSV。实现改变逐项披露，不把自制弱版本冒充原方法。 |
| D：未来候选 | **当前未指定，因为 gap 未成立。** 只有自然失败证据暴露 A–C 无法解决的明确机制后再冻结 D。D 必须共享同样历史、反馈、初始库和消费者，不得额外获得未来题目或 gold。 |

若暂时无法实现 C，则可以先做 A／B 的产品决策试验，但不能据此声称超过研究最近邻。若 C 已足够解决问题，直接采用它，项目可定位为可核验的原生接入与运维系统。

### 4.3 最小判别流程

- **数据冻结**：先分开发历史、方法选择集、最终 test。按 issue／程序模板去重；不能仅换实体名。至少同时含会用到既有程序的相关任务，以及容易被过度套用规则的近邻反例。跨仓库泛化必须另留整库，不能从同仓库题面随机切分后宣称跨库。
- **第一轮小样本**：例如 4 个独立仓库／工作流块，每块 4 个封存后续任务，每臂独立重复 2 次，即每臂 32 个结果槽。重复运行数不等于 32 个独立任务，实际只有 16 个任务、4 个块。该轮只用于发现大回归、接入失败与成本不合算；不能凭它证成 5 个百分点的小收益。
- **相同历史**：用于比较记忆表征／选择机制时，各臂先消费同一份历史，冻结库后跑 test。若比较真实在线整策略，则独立跑相同任务流，允许历史自然分叉，但把整条流视作随机化／重采样单位，不再声称只隔离某个编译器。
- **原生执行**：使用一个固定的 CLI／模型快照先做；首轮完成后再用冻结 artifact 在另一消费者验证。不能同时替换原生 loop、工具和模型后归功于记忆。
- **预算匹配**：在不看 test 的开发集选择至少两个总成本档位。每臂遵守同一可计量上限，记录实际值及超额；未花完预算不灌水，允许简单基线用在 actor。原生 CLI 若无法观测或约束完整费用，必须明确“预算未充分对齐”，不能给出成本优越性结论。
- **封存测量**：test 的最终判分只用于报告；测试分数不得驱动换版本、再写技能或对失败题二次提交。调参需要新开发版本与新的最终评估。
- **扩大样本条件**：只有原生接入可信、自然痛点存在且小样本没有被 A／B 支配，才根据开发集的配对分歧率与块内相关性预设确认样本量。报告分块差值、置信区间和所有失败，不以某次 seed 最好值做结论。

延迟／噪声反馈应先作为**分层条件**，不要先作为创新标签。若真实系统确有延迟 CI，冻结事件到达时间，所有方法在相同时间能看到同样信息；预设“现在必须决策”和“可以等终态”两种业务代价。若可以无损等待，B 的简单等待就是正确强基线。模拟噪声必须单列，不能把随机 label flip 当真实反馈质量。

### 4.4 预算账本

至少记录 `历史采集 + 反思/压缩 + 候选生成 + 检索 + judge + 验证探针 + 失败与废弃候选 + actor 执行 + 修复/重试`，并记录输入、缓存输入、输出、可观测的 reasoning tokens、费用、工具运行时间和墙钟延迟。

分别回答两个问题：

1. 固定一次性历史和已建库，后续每题是否节省？
2. 从开始采集到部署期结束的总支出，何时回本？

如果没有足够复用次数覆盖制作成本，就不能称为总成本下降。把昂贵建设“离线化”不会让费用消失。成本只按实际观测可支持的维度比较，不把不同模型的 token 数直接当同等算力。

## 5. 失败定义与必须撤销的主张

**任务失败**：首次提交未通过预先固定的真实验收；含错误产物、漏做必要修改、测试失败、超预算终止。依赖／工具／权限故障另标原因，但保留在部署效果分母；若事先定义为实验设施异常，报告完整数目，并在在线流设置下说明恢复对后续记忆的影响。

**负迁移**：同任务配对中基线成功、经验策略失败。除净成功差值外，还要报 `基线成功→策略失败` 和 `基线失败→策略成功` 两个分母；总体持平可能掩盖对已稳定行为的损害。

**更新失败**：生成无效 artifact、接入后没有被暴露、收到反馈后错误修改、接受候选在后续任务退步、候选评估成本无法回收。拒绝所有更新可以很安全，但若不优于冻结库，就不能叫有效学习。

出现以下任何一种结果，都要撤销相应主张：

- B 与自动方法相当或更好：撤销“需要自动演化”，采用固定清单。
- A 在同成本档位相当或更好：撤销“经验维护有净收益”，增加 actor 预算即可。
- 只在同题重试、同模板变体或近乎复制的训练分布获益：撤销未见任务泛化。
- 只有隐藏 rubric／gold 可用时获益：撤销真实部署可用性。
- 加入所有被拒候选、judge、维护和探针费用后优势消失：撤销效率优势。
- 随机可用性实验无效，但自选 use 组很强：撤销技能因果有效性，只能说相关。
- 仅对 self-judge 分数有效，最终真实验收无改善：撤销任务能力提升。
- 加入 GRASP／SkillSV／SkillEvo 后差异不成立：撤销方法创新，保留原生接入工程贡献。
- 效果随模型／CLI 版本或 task order 改变而翻转：把结论缩到已测版本和分布；不能保留“通用增强”。
- 置信区间覆盖无效或实际不值得的收益：结论是“证据不足”，不能写成成功，也不能自动写成方法完全无效。

## 6. 对两个看似可做的方向的拒绝式判断

**方向一：弱反馈下先归因再更新。** SkillEvo 已做 repairability attribution，Evo-Harness 已做反馈粒度对照。新的延迟或污染条件可以形成有用的部署研究，但目前没有本地发生率、代价与现成方法失效证据。最致命替代是简单等待终态并附正确来源标识；若这就解决问题，复杂置信控制没有立项理由。

**方向二：有限预算用随机撤销探针定位有害技能。** GRASP 已有当前库重跑的因果基线，SkillSV 更直接覆盖结构有效反事实、长度控制与带噪预算估计。单独对比 SkillSmith 观察性 utility、人工逐项 LOO 或随机探针已不够。若未来确有新方法，必须在相同候选、相同任务反馈与相同 rollout 费用下超过 SkillSV，以及 GRASP 加结构合法逐项消融；还应证明不是只适用于某个人工交互模式。

因此此轮不推荐把任何一个包装成新研究方法。**最致命的整体攻击是：你做出了一个管理更多经验和评测的系统，却没有证明用户遇到的失败由缺失的经验机制造成；收益也可能被一页短清单或把预算还给现成 Agent 完全解释。**

## 7. 可保留的项目定位

若用户确实需要，可交付为“服务现成 Coding Agent 的可审计经验部署系统”：冻结消费者与 artifact、接入原生技能、记录真实暴露、隔离反馈与最终验收、保存版本和回滚证据、统一计算完整成本。这些是可以执行验收的系统性质。

研究主张应等到真实工作流上的判别结果出现后再定：正结果说明在哪种复用密度与成本条件下值得维护；负结果说明何时固定清单或额外 actor 执行更合算。两者都比“有反思、有门控、有持久化，所以能自我进化”更可信。

## 8. 第二轮裁决：改做“原生 Coding Agent 既有 Skill 库事故诊断工具”是否成立

**科研立项：NO-GO。完整工具实现：当前也 NO-GO。** 这个转向移除了过强的“自动学习”承诺，但没有凭空产生研究 gap。现有证据没有证明用户反复遭遇了技能事故、人工诊断成本很高，或现成反事实／回归工具无法处理。现在应先人工复盘极少数真实事故，不应先建设一个需要事故来证明价值的平台。

### 最强的便宜替代

一个可重复执行的普通 runner，加版本快照、`rg` 检查真实技能读取与相关工具操作、人工对照三份轨迹：**当前库、上一个可用库、当前库撤掉本次可疑改动**。它不需要自动根因模型、价值估计、知识图谱或自演化。

如果怀疑只是技能没有加载，读取可见目录／catalog／调用日志就足够，应直接修接入。如果需要估计内容贡献，则现成 SkillSV 是必须面对的研究基线；若需要接受／拒绝修订，GRASP 已是强基线。增加一个 UI、统一 manifest 或支持两种 CLI 可以有工程价值，但不单独构成科研新意。

### 最小判别实验：先证明诊断需求，而非训练一个诊断器

选 **2 个自然发生的疑似回归事故，加 1 个没有导致退步的真实库更新作为阴性对照**。病例应有之前的正常产物／任务结果和本次失败轨迹；不能先植入坏规则再宣称生产需求已成立。

每个病例做三臂、每臂两次独立执行，共 **3 × 3 × 2 = 18 个任务槽**：

1. 当前库：确认症状是否能再次出现。
2. 上一个可用库：确认整个库更新是否与结果有可重复差异。
3. 当前库撤销被怀疑的那次改动：检查是否足以恢复，且剩余依赖完整。

三臂固定任务、repo snapshot、模型／CLI、工具权限、公开反馈与执行预算；随机交错顺序，并为每次运行提供全新状态。保留所有首次结果与费用。本次同题重跑属于**诊断成本**，不能计为新任务学习收益。若撤销明显缩短上下文，只有要声称内容机制时才另加等长度对照；工具只承诺可操作回滚时，可以先报告整体撤销效果及该限制。

让一个熟悉该工作流的人在限定时间内，仅看原始失败轨迹、库 diff 与版本元数据给出初步诊断；未来工具也只能看到相同输入。两者先输出可疑改动、证据链、建议动作和“无法判定”的置信边界，再解封三臂结果核验。需要额外回放才能确诊时，允许两者请求同等回放，并逐次计费。正确答案不能只由“看起来合理”的解释或 LLM judge 决定。

若只是整库回滚恢复，最多定位到版本；若合法的单项撤销也恢复，才获得该条目在**当前库与当前任务**下有害的证据。不能推导它对所有任务都无用。若两次重跑相互矛盾，应标记不稳定并估计补充诊断成本；18 槽不是高精度统计证据。

### 判定指标与停止条件

比较首个有证据支持的可执行诊断所需的人时、模型／工具费用、回放数、误指控次数，以及阴性对照上的错误回滚建议。可复现的证据路径本身也是产物，但“生成了一份报告”不是诊断成功。

- 两个自然事故都不能稳定复现：当前不适合承诺自动归因；先定位模型／环境漂移。
- 普通 runner 与十几分钟人工检查已解决：没有证据支持完整诊断平台，保留小脚本即可。
- 常见原因都是路径、catalog 或权限错误：做确定性的接入检查，不包装成技能价值研究。
- 工具为了得到同一诊断必须花更多回放预算：不得只用更快的人工阅读时间声称效率提升。
- 只有人工注入错误能让诊断器显得有效：只能声称合成故障测试通过。
- 唯一可重复收益是文件快照、版本绑定、日志整理：这是明确的工程贡献，不能改名为新因果方法。

**最终建议：此时不实现新诊断系统，也不承诺科研 gap。** 先用上述便宜流程查三个病例。只有这一步实际暴露了无法被脚本、人工回放和现成方法解释的重复障碍，才有理由重新定义问题；本审查不替尚未出现的障碍预先命名一种方法。

## 9. 工程目标澄清后的复审：仓库级经验维护

**新目标是解决真实重复维护问题，不要求新算法；因此前文基于缺少方法新意的 NO-GO 不适用于本工程立项。建议开展有上限的工程试点，暂不建设通用平台。** 复用现成方法完全成立，项目要证明的是交付价值。

**唯一推荐主终点：质量门槛通过后，每个分配任务的完整交付成本。** 固定观测期内，将建库／配置、模型／工具、经验维护，以及人工 review／纠正／补救的人时全部计入，再除以全部分配任务数。人工按事先固定的工时单价折算，同时保留分钟和费用原值；不得用事后选取的单价制造优势。未完成任务保留在分母，并按预设完成率与时限计入质量判定；门槛不通过时不得判为成本胜出。首次成功率和重复纠正次数作为解释指标，不另设多个主终点。

### 最小四臂

| 臂 | 冻结定义 |
| --- | --- |
| A 原生 | 当前可用的原生 Coding Agent，保留共同的正常工具与基础指令，不新增本项目跨任务经验机制；允许将省下的维护预算用于执行。 |
| B 静态短清单 | 同一批初始历史提炼成一页项目清单；公开适用范围，后续不改。制作与人工整理成本入账。 |
| C 现成强基线 | 选定一个适合该工作流、配置合理的现成演化方法，例如 Evo-Harness，接入同一个原生消费者，按其机制从已结束任务的实际轨迹与反馈更新。适配改动公开，不能删掉核心能力制造弱基线。 |
| D 候选工程流程 | 拟交付的仓库经验维护流程。相对 C 的变化逐项冻结，例如反馈绑定、项目适用范围、维护节奏或版本恢复；保持编译模型和消费者相同。若只是同一方法的接入自动化，比较节省的操作／维护人时，不虚造准确率新意。 |

先冻结一类维护任务、同一份初始历史和真实后续任务清单，按时间分开发／选择与最终评估；不同 issue 才算后续任务。四臂在相同 repo snapshot 上执行相同任务流，各自隔离，只能利用自身已经结束的过去任务反馈。后续历史自然分叉是整体工程策略的效果，不再解释为单个算法模块的纯贡献。review 尽量隐藏实验臂，纠正与技能维护分别计时；同一 reviewer 重复看同题会熟悉答案，应交错分配并记录顺序。

四臂共用模型／CLI／工具权限／普通验收标准，以及预设的任务与整批总预算上限。C／D 的反思、judge、被拒候选、验证、重试都从该池扣费；A／B 可把余量用于正常执行。先在开发任务上确定上限与维护频率，不能看到最终失败后给 D 单独加预算。公共测试和真实 review 可以在任务结束后用于未来更新；未来任务、隐藏验收与 gold 不进入更新输入。

### 分阶段验收

1. **痛点成立**：用已有记录确认至少一种错误在不同维护任务上重复需要人工纠正，明确哪些属于技能可承载的项目程序。若都是权限／服务故障，改做相应工程修复，不搭经验系统。
2. **接入与量账成立**：少量任务验证原生加载、真实暴露、反馈到达、版本隔离、完整计费与人工计时。只读到 SKILL.md 不是收益证据；成本或来源漏记则先修观测。
3. **小型四臂判别**：用封存的后续任务试跑，先识别明显质量退步和成本浪费；小样本只作筛选。质量采用相同测试及盲审标准，预先指定严重回归零容忍、完成率非劣容忍度与时间上限。不能在结果出来后放宽门槛。
4. **工程交付成立**：冻结选中的流程，在下一批真实任务验证质量门槛与主终点。D 相对 A／B 降低完整成本，并相对 C 有实际的接入／维护人时、可靠运行或成本优势，才支持候选工程贡献。若只证明 C 有效，就交付 C 的薄接入并如实归功，停止添加未证实机制。

**明确否决条件**：静态清单或原生臂在同质量下更便宜；节省的人工纠正被建库／验证／维护开销抵消；收益依赖同题重试或未来验收泄漏；候选需要更强模型或更多免费反馈；误更新导致质量门槛失守；或人工 review／费用账本无法可靠测量。证据不足时结论是继续观测或缩小交付，不宣称已减少维护成本。

这一项目的工程贡献可以是：把原本反复由人讲解的仓库程序，变成可维护、可回滚、能实际节省交付成本的原生项目 Skill。算法复用不构成否决；没有真实需求或净收益才构成否决。
