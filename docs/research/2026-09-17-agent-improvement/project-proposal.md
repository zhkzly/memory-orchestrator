# 仓库级经验维护：面向现成 Coding Agent 的项目提案

日期：2026-09-18。用户已明确：独立解决真实问题，论证和实验扎实，不要求发明新算法。本文是最新的工程项目提案；此前“缺少方法首创”的裁决只约束原创性表述，不自动否决工程项目。

状态：可以进入问题验证和方案收敛；真实痛点强度、系统收益与必要性尚未实测。不是已完成项目的论文，也不是产品实现授权。

## 一句话目标

让现成 Coding Agent 在同一类仓库维护任务中，复用此前经执行或人工 review 支持的操作经验，减少开发者反复纠正，同时识别无收益或导致回归的更新。

第一批消费者是 Codex、Claude Code；建议先在一个客户端、一类有可重放环境与独立验收的仓库任务上建立证据，再验证第二个客户端。两种客户端兼容与经验能跨客户端迁移分别验收。

## Background：为什么这个问题有意义

原生 Coding Agent 已能执行复杂任务，也能通过项目指令、记忆和 Skill 保留指导。维护者仍可能需要对相近任务重复补充项目约束、纠正排查方式或要求更合适的验证过程。已有论文说明经验可改善后续执行，也可能产生负迁移，且维护成本可能抵消收益。

这里的项目对象是“某类工作流中的重复纠正”，不是所有 Agent 的一般记忆问题。不能从论文负例推断用户已经存在同样痛点；必须保留真实案例、原有规则以及后续结果。

## Problem：第一版具体解决什么

建议首次锁定一个 Python 服务仓库的 API/工具接口变更：新增或修改字段、状态、错误分支，并完成测试与 review。选择理由是边界可冻结、代码和测试可重放、纠正可指向具体遗漏；这是试点选择，不是已证明有收益。如果该仓库近期没有这类真实重复任务，就按其真实历史选择另一类，并在实验前冻结类别。

所选工作流应有：不同 issue 中重复发生的可操作问题；原任务状态能重放；正确产物可由既有测试、独立检查或维护者预先确认的验收判断。第二个仓库和第二个客户端留作后续外推验证。

不优先处理可以直接固定成一条命令、lint 规则或确定性 hook 的问题。若任务只是“始终运行某个测试命令”，静态规则是必须先用的合理办法。

待检验的用户诉求是：“我已经纠正过类似问题，希望下一次相关工作自动用上；也希望知道新的经验是否造成了其他返工。”这是一句产品假设，尚未被用户样本和计时确认。

## Gap：系统的切入点，及其证据边界

候选部署缺口是：从一次真实纠正，到形成适用范围明确的经验，再到确认后续任务确实受益，维护者仍可能承担重复的输入整理、规则修改和验证工作。

现有原生记忆、OpenViking、Evo-Harness、GEPA/GRASP 都是有效替代或可复用组件；本项目不声称它们没有学习、Skill 更新或验证机制。真正需要回答的是：在选定工作流中，现成组合是否已经足够；若不够，剩下哪一步代价高、容易出错，最小系统能否减少它。

如果现成配置或短清单就解决，不另造同类核心；可以直接基于它们交付。独立项目的价值由问题和结果建立，不由是否从零实现数据库建立。

## Research Question：可以判定真假的问题

在相同历史、消费者版本和完整成本约束下，反馈驱动的仓库经验维护，能否比原生 Agent、同证据构造的静态短清单，以及适用的现成记忆/演化方案，更少地需要人工纠正，并保持后续任务的首次验收质量？

预期的系统收益是用户处理成本下降。任务成功、回归和制作/维护成本共同约束这个收益，不能只报告 memory 数量、Skill 读取率或内部结构分。

## Method：只保留三段必要行为

### 1. 采集可用于学习的证据

把一次任务的公开要求、可见交互、实际改动、测试/验收结果及人工纠正绑定到同一次运行；记录当时 Skill 版本和消费者配置。没有结果或基础设施异常时保留 unknown，不把 Agent 自述当正确性标签。

系统首先判定反馈是否支持某条可复用经验。确定性接入/配置错误应交还普通工具修复，不能预设每次失败都必须生成 Skill。

### 2. 维护适用范围明确的项目 Skill

复用 SkillFlow 的文件补丁接口，或 Evo-Harness 的反思/批次整理机制，根据已有库与证据提出小幅修订。内容应说明何时适用、关键操作、验证要求与已知例外；优先更新已有指导，允许无修改。

Skill 文件与原始证据分离：前者供 Agent 执行，后者供审查和追溯。初版可以使用本地文件，未来若 OpenViking 已满足存储需求则直接复用。新的项目价值不依赖自建检索数据库。

### 3. 用后续行为验证是否值得保留

在隔离目录中保留旧版和候选版，使用已声明的开发任务与回归任务判断修订；参考 GRASP 等现成准入方法。通过后才进入所测试的部署配置，保留恢复旧版的证据。

对最终未见任务的评分只用于报告，不反向参与选版本。客户端实际看到了哪些文件、是否读取及实际执行了什么分别记录；不能把读取直接计为采用或有效。

这些机制全部具有已有方法来源。本项目的个人工作应明确落在实际工作流定义、原生日志与反馈适配、证据契约、版本交付、任务验收和效果实验上。

## Evaluation：把替代解释放进实验

| 比较对象 | 用来回答什么 |
| --- | --- |
| 原生 Agent，保持已有能力 | 是否有必要增加经验维护；省下的预算允许用于正常执行。 |
| 同历史构造的静态短清单/Skill | 自动更新是否胜过一份人工精炼的稳定规则。 |
| 最接近的现成方案 | OpenViking 原生接入或适用的公开演化方法是否已经足够；应按真实场景选一个强基线，不全部安装后堆数量。 |
| 候选系统 | 增量究竟来自输入准备、更新策略还是验证/交付；选定后保持其他条件一致。 |

主终点采用：通过预设质量门槛后，每个预先分配任务的完整交付成本。固定观察期，将接入/建库、模型工具、经验维护以及人工 review/纠正/补救计入，除以全部分配任务数；未完成或异常任务不能从分母删掉。若把人工时间折为费用，提前固定工时单价并同时报告原始分钟和费用，不能事后改权重制造优势。

首次独立验收率、同类重复纠正和配对救回/回归作为解释与质量指标。质量门槛不通过时不能以“更便宜”胜出；小样本只用于筛选，不能证明非劣化。若第一阶段无法可靠获得人工时间，只能先报告任务表现与可观测成本，不能写成已降低用户工作量。

同一历史不能把隐藏答案、最终测试或人审修正免费多给候选组。维护调用、失败候选、所有探针、重试和用户审阅时间均入账。固定 repo/模型/CLI/工具权限，独立状态并交错执行；多个运行次数不冒充多个独立任务。

只有基础接入与大幅回归检查通过后，才扩展未见 issue、任务顺序、仓库与第二个客户端。少量先导数据用于决定是否继续，不能支持普遍泛化或小幅统计提升。

## 可成立的贡献与不能预写的结论

验证后可能成立的贡献：

1. 一套真实工作流中可复核的“纠正—经验修订—后续结果”资料与评价协议。
2. 能被现成 Coding Agent 消费的经验维护系统，含明确的反馈、版本与验收边界。
3. 相对原生方法、静态规则和现成方案的效果/成本证据，以及何时不值得自动更新的边界。

当前不能声称：首次 Skill 演化、首次回归门、通用变强、零回归、跨模型无损迁移、任何尚未测得的提升百分比。

## 立项步骤与否决条件

第一步：冻结少量真实重复纠正案例和原有规则，使用便宜替代，记录仍未解决的共同步骤。单纯做同题复现只能验证集成，不是学习收益。

第二步：只实现那个必要步骤，接一个客户端形成真实端到端样本。反馈整理、生成 Skill、实际加载、任务结果必须连通；不能用格式测试代替。

第三步：按上述对照在封存任务上测量，得到结论后再组织论文式介绍与简历。发现无净收益时采用静态规则或现成产品，不追加模块保护选题。

停止条件：不存在真实重复问题；短规则已足够；主要错误可由测试/hook直接阻止；现成方案同效同价；维护和验证成本高于节省的人力；只有已见题或合成故障上出现收益。

## 面试叙事的真实骨架

“在某类仓库维护工作中，我观察并记录了重复纠正的具体成本；比较原生规则和现成工具后，发现剩余的某一步瓶颈；我复用已有方法并实现了必要的接入与验证；通过冻结任务和完整成本对照，得出了适用范围与失败边界。”

上面的观察、瓶颈和结果都要由后续证据填入。现在它是研究设计，不是可直接写成已完成经历的陈述。

## 三位审查员在用户澄清后的意见

- [文献审查](novelty-review.md)：允许条件性工程立项；明确引用已有方法，并把 OpenViking 作为可复用底座和强基线。
- [产品审查](product-review.md)：先一个仓库、一种 Agent、API 变更工作流；真实来源、后续收益和第二次更新的维护成本都要验收。
- [有效性审查](validity-review.md)：四臂对照，完整成本入账，先守住质量再比较净收益。

共同意见是允许有上限的工程试点，不是断言需求或收益已成立。主终点和首次场景是本提案的取舍，不用多 Agent 一致意见代替执行证据。

## SkillSmith 深读后的候选方法补充

2026-09-18 的 [论文精读](../../references/skillsmith-paper-independent-20260918.md) 和 [源码核查](../../references/skillsmith-code-deep-review-20260918.md) 表明，SkillSmith 不应只作为“较重的回归门参考”。它把操作知识、可执行工具和负经验一起维护，并把依赖的 Skill/Tool 修改作为同一候选验证；公开代码也有 OpenCode CLI 路径。

因此，若真实纠正显示瓶颈在可复用脚本/适配器能力，而不只是文字指导，应优先参考这种联合候选与依赖迁移方法。可演化边界是项目拥有的 helper/wrapper/tool server，不是假定能修改现成 Agent 内部工具。Skill-only 和现成工具应保留为对照，只有目标工作流的执行证据才决定是否加入工具演化；不因论文完整就照搬生态方程、所有生命周期操作或多分支搜索。

这更新的是方法参考优先级，不将当前项目改成论文复现，也不增加已完成能力或效果声明。
