# 长轨迹先分层再学习：针对性核查

日期：2026-09-19。状态：本轮核心核查完成，候选设计未实施；本轮只补研究记录，不修改产品、提示词、HTML或运行参数，不调用实验模型。用户追问的是学习器如何处理超长源轨迹，不能用“保留原始日志”或“下次按需读取 Skill”代替答案。

## 三个问题与检索边界

1. 已有项目在事后提炼前实际进行哪些截断、分块或模型摘要？压缩器自己如何避免超限？
2. 文献中的 hierarchy 是输入预处理、记忆产物的组织，还是正在执行任务时的上下文管理？
3. 哪些证据支持分层，哪些负结果或实现缺口反对盲目增加摘要层？

以现有 ReasoningBank/SkillFlow/SkillSmith 冻结源码审计为直接对照，另分工核查 SimpleMem、Tree-of-Experience、ACON、Context-Folding；本文件核查 STAIR，并用 HMT 说明“层次结构不等于有界预处理”。web 与第二搜索引擎用于发现，结论回原论文/作者源码。没有用二手综述的推荐当成效果证据。

## STAIR：确实有离线逐层抽象，首层输入预算仍未证实

来源：[论文 v1](https://arxiv.org/html/2607.29658v1)，2026-07-31，方法 III-A/B，实验 RQ3/4，局限 V。以下为【原文级/作者实验报告】，本轮未复现。

方法流程：成功修复轨迹先拆成定位、规划、执行与验证三种阶段；叶节点保留 thought/action/observation。LLM 将相邻、意图一致的步骤分组，另一抽象操作生成含修复意图、关键动作、适用条件、常见陷阱的父节点。重复对父节点分组和抽象，直到根节点数量不超过2。检索时混合使用不同抽象层，而非只留下最高层摘要。

这与“先分层处理，再复用经验”的主张直接相关；但论文描述的 `G(L0)` 首次仍要处理原始步骤。所查正文没有给出这个输入超过模型窗口时的块大小、溢出或续读实现。按阶段拆开不能保证每个阶段足够短。精确题名/作者代码检索和论文链接检查尚未定位到官方公开实现，因此不声称代码已经解决该边界，也不据此断言作者没有内部实现。

RQ4 使用125题的分层难度子集，报告完整多层方法100/125，原轨迹变体72/125；这支持该设置中复用抽象产物的收益，不能单独证明摘要器如何安全处理任意长度，也不是只改变预处理字数、其他条件完全固定的摘要保真评测。RQ3报告加入计划后仍有回归，作者将部分归于计划覆盖不完整。不得把平均增益解释成压缩无损。

本论文主要从成功修复过程构建经验，不能据此声称也已解决失败轨迹中的局部归因。离线预处理有独立成本，论文报告约每条源轨迹0.44美元；这是作者特定配置的估计，不是本项目成本。

## HMT：另一种分层，仍需追问分段器输入

来源：[Enhancing Web Agents with a Hierarchical Memory Tree v1](https://arxiv.org/html/2603.07024v1)，2026-03-07，III-C。

【原文级】构建从成功网页轨迹开始：归一化任务意图；LLM把轨迹切为连续子目标，并校验覆盖、顺序、连续性和最小长度；然后按观测中的页面元素属性，将每一步操作抽象为语义动作，形成 Intent/Stage/Action 三层。层次的用途主要是跨网站复用、区分规划与操作细节。

【核验边界】Algorithm 1 写作 `Segment(τ)`，所查段落没有说明超长 τ 如何在进入该模型调用前按 token 有界切块。结构化JSON输出可以辅助结构校验，不意味着语义确定或摘要无损。当前没有定位到官方公开实现，因此只引用方法，不编造源码级阈值或接口。

## 对当前项目需要改正的表述

【我们的判断，尚未实施/验证】先前“抽一些事件→提炼→有疑问再补读”的说明没有回答全局顺序如何被覆盖、提炼器怎样发现应该回查哪里。应先明确一个有界的轨迹转换阶段，再讨论从转换结果学习。原始归档、每段处理和上层经验是不同表示，不能共用“完整轨迹”一词。

分层建议是两个模型职责：局部阶段按有界片段描述发生了什么，汇总阶段结合反馈及多个片段判断哪些做法可复用。局部输出要保留目标版本、动作/观察、局部结果、未决问题、来源位置；全局失败标签不自动等于每个局部步骤失败。工具结果中的关键数值、断言和代码差异要保留原文引用，不能只相信 Actor 后续复述。

压缩不必是“每个结果先调用一次模型”，也不必递归建任意深树。先确定性去除重复请求快照和大块非必要包装，再按完整交互轮及 token 预算切分；需要时对局部片段生成结构化摘要。上层只读这些局部记录和必要的原文例外。短而可容纳的轨迹仍可直接处理。以上是工程选择，不是所查论文共同规定。

独立来源：[离线层次核查](offline-hierarchy.md)、[运行时压缩核查](runtime-compression.md)。

## 开源实现与反证

SimpleMem 固定源码先按消息数切窗，再每窗一次调用直接提取记忆；顺序模式仅带少量前窗条目，并行模式各窗结果拼接入库，没有所假设的跨窗口二次LLM归纳。W=40/overlap=2是该源码默认值，论文另有W=20；所查builder与SDK包装器没有输入token上限。它面向聊天事实记忆，不能直接作为工具轨迹失败归因或Skill学习的效果证明。[实际写入器](https://github.com/aiming-lab/SimpleMem/blob/db80b6a7c591e0ea730a058e9f5fc4eb06572299/simplemem/core/memory_builder.py#L121)。

另一个反证是 [The Complexity Trap v3 摘要](https://arxiv.org/abs/2508.21433v3)：作者在SWE-agent/SWE-bench Verified的5种模型配置中比较旧观测遮蔽与LLM摘要，报告前者相对无管理执行器约减半成本，并匹配或略超摘要的解题率。该结果约束“LLM摘要必然优于简单处理”的假设，但对象是运行时上下文管理，不是事后经验提炼；不能据此给本项目直接删除tool result背书。本文只引用该明确范围，未复现作者数字。

最可靠的归纳不是“所有系统都先做层层摘要”，而是：实现确有预先裁剪、窗口提取和逐层抽象等不同选择；输入有界、事实保真与经验可复用需要分别检查。层次化的最终产物无法替代首层输入预算设计。

## 从研究约束出的候选数据流

【方案讨论，不是已经实现】使用两层模型职责即可，避免为了“分层”新增任意深的搜索树。输入切分要发生在首次模型调用之前，不能要求模型先读完整原始日志再告诉程序如何分块。

1. 程序归一化增量事件；重复的SDK历史快照只记录一次，但真实重复操作的发生次数与位置保留。按已知任务/目标版本分开。
2. 按完整交互轮和模型输入预算切片；单条过大的工具返回先按行/记录/字段分页或提取确定性元信息，保留所有原始位置和省略标记。消息数量上限不是token上限。
3. 每个有界片段生成局部结构化记录：当时目标、关键动作、观察到的事实与变化、局部结果、未决事项、来源引用。该层描述发生了什么，不把全任务的失败标签强加给每一步，也不提前写普适Skill。
4. 上层读取局部记录、任务约束、可信反馈和有关旧经验，比较片段间的尝试/修正与结果，形成条件化经验。局部记录仍过大时分批处理并保留源引用，不把全部原始tool result再次拼回来。
5. 仅在某项候选依赖被省略的具体事实时回读原文；候选随后仍走已有Skill修改和独立验证流程。摘要存在引用不意味着语义充分或因果已证，缺证要保留未知。

这条路线把主要学习输入放在局部整理后的记录上；补读是少量核对机制。压缩器仍需阅读所负责片段的相关原始信息，分层减少单次负担而不会使总阅读成本消失。按需使用压缩，短轨迹无需强制经过额外模型摘要。
