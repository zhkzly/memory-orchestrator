# 当前链路与讨论建议

核验日期：2026-09-19；产品基线 `69980a68ac702516028bf9d480ca1462c8ca0862`。本轮仅检查代码、已有实验工件与一手资料，没有运行模型、改产品/提示词/HTML、重新评分或读取最终 probe 的答案。本文件的建议尚未成为实施契约。

## 已实现的轨迹路径

需要区分三件事：完整保存已观测日志、程序扫描/索引这些日志、把哪些正文交给 LLM。当前不是把整段原始日志都交给学习模型，也不是逐块 LLM 摘要再汇总。

1. 保存观测到的任务、动作、工具返回、产物和反馈；建立任务/目标版本、事件、调用配对和来源位置索引。JSONL 路径支持增量磁盘索引与有界正文读取。
2. `evidence.build_packet()` 优先选任务要求、反馈、显式失败等材料，按同 episode/call_id 组织动作与返回，再覆盖轨迹的不同时段。正文、可补读目录、关系信息均占预算；保留来源引用与截断说明。
3. `learning.py:407–439` 将 packet、已提供的反馈、相关经验、可读目录交给 `extract_v1`。只有返回 `needs_more_evidence` 才调用 `expand_packet`，预算耗尽则放弃。目录不等于正文已读。
4. 后面的 diagnose/propose 使用已提供证据与经验；不能把 extract 的补读能力描述为所有节点都能自由浏览原日志。

[证据选择](../../../src/memory_orchestrator/evidence.py)、[学习编排](../../../src/memory_orchestrator/learning.py)、[试验策略](../../../examples/gdpevo_pilot/run.py)。

本次 pilot 参数是初始 packet 42,000 字符、单片段 1,800 字符、目录最多 24 引用；最多补读一轮、请求 3 项；扩展包 60,000 字符。这些是包/片段上限，不能当成整个 SDK 输入的精确 token 上限。当前模型输入还包含 schema、提示词及其他字段。

已有工件：136 个原始事件，修复后初始包覆盖 20 个事件；两个 extract 都返回空 `read_requests`。紧凑 packet 41,582→41,246 字符，但实际 SDK 消息 61,004→62,078 字符，不能称整体压缩收益。[试验报告](../../experiments/gdpevo-context-pilot.md)、[Teacher 审计](../../../.trellis/tasks/archive/2026-09/09-19-benchmark-context-pilot/research/revised-teacher-audit.md)。

## 第一处缺口：按调用配对还没有连成同一项业务判断

当前支持显式 parent/resource 关联和有界依赖查找，但 pilot 的 Actor 事件只提供 call_id 等字段，没有订单/SKU/仓库的资源关系；学习策略也没有设置 `dependency_lookup`。因此不能说核心接口有依赖查找，实验就已经用了语义依赖取证。

工件中订单 SO-70049 的仓库为 WH_WEST，行 SKU 为 NW-1053、NW-1029、NW-1009、NW-1034；所选 product NW-1047 与 inventory NW-1047/WH_CENTRAL 虽能互相连接，却不属于这份订单。客户与订单能连接，但没有完整的“订单行→同 SKU 产品→同仓库库存→输出字段”链。这里不能推断 Actor 当时查错了仓库，只能判断 Teacher 看见的材料不能重算该订单的库存决策。

**已确认的是证据入口缺口。尚未证实的是它对分数或 generic Skill 各自贡献多少。** 提示词、反馈粒度、Actor 随机性也可能影响结果。

## 第二处缺口：官方反馈本身只有聚合判定

核查的是开发任务 train001 的 [固定官方评分器](https://github.com/Prism-Shadow/GDPevo/blob/56d60ae4ae5e067d1ec0ee1f850622e69f422179/data/task_groups/task_group_007/train_tasks/001/eval/evaluate.py)。它先按 order_id 规范化记录，对金额舍入、SKU 集合排序，再计算 8 组加权判定。例如库存项用所有订单的 inventory_status 和 shortage_skus 比较后取 `all(...)`。

输出包含总分、得分权重、总权重，以及每组的 id/weight/matched/normalized_weight。没有输出具体错误订单、字段路径、actual/expected 差异或原因。

本项目 `dataset.py:150–197` 实际保留了官方 stdout/stderr、解析结果、评分器和产物摘要。**细粒度反馈不是适配器拿到后单纯在提示词中丢掉；上游当前就没有发出。** 评分器通过某组可以构成成功证据，但该组失败不能唯一确定记录级错误或计算原因。

增加训练期诊断是一项反馈协议变化，不是重写一句 prompt。若采用，应保持原评分定义不变，在训练/开发可见范围中输出与同一判定规则一致的差异：判定项、产物/记录身份、字段、实际值、参考值或约束、来源。不能直接使用通用 JSON diff，忽略评分器的排序/舍入等语义。Teacher 可读的训练反馈与 Actor 输入、最终测试答案继续隔离；结果需注明新增了何种监督信息。

凡参考答案或字段差异进入 Teacher 并用于修改的案例，均属于学习/调参材料，不能再计为独立泛化证据；冻结回归与最终测试的反馈可见性需按事先约定保持。

没有答案的实际环境可以使用执行测试、工具状态、环境变化或明确人工纠正；缺乏这些信号时保留未知。模型自评可作代理反馈，但不得与可执行验收等同。

## 建议如何组织长轨迹，尚未实施

分析单元先按 task/goal revision 限定，再围绕具体输出决策取证，而不是先要求全会话摘要。若单任务完整表示可容纳，也可以直接作为输入或对照，不能预设“裁得越少越好”。

`绑定目标与产物 → 定位反馈项 → 查相关实际输出 → 拉取同对象输入/动作/返回 → 判断仍缺什么 → 有界补读或保留假设 → 比较相关成功/失败 → 提出局部经验/Skill 修改`

业务对象键由任务适配器提供，核心复用现有事件引用/资源关系；不需要为这次问题先增加图数据库或通用因果引擎。跨调用的同对象关系也不等于已证明因果。成功对照和反例同样需要进入材料，避免只为既定解释挑证据。

当一次 GET 含很多记录时，按记录/字段保留来源和查询条件比任意截前 1,800 字符更适合计算任务；不应靠模型摘要替代需要精确重算的数值。可选的分层摘要只作导航，重要判断仍回到原证据。预算用完是缺证，不是默认原因成立。

模型输出应分别表达：观察事实及引用、待解释的失败、可区分的原因假设、缺失材料、条件化经验。当前 `completed` 可以只表示提炼出有限操作经验，不能被下游自动理解为业务根因已查明。引用存在校验也不等于引用足以支持结论。

## 文献对长上下文的补充

[Recursive Language Models v2](https://arxiv.org/html/2512.24601v2) §2 将长输入放在外部环境，模型通过程序查看与分解，再对子片段调用模型；这支持将存储与当次模型上下文分开。它不是已验证的轨迹归因器，§6 也明确自然长上下文任务和实现机制仍待探索，实验只使用一层递归。我们无需因此引入完整 RLM 框架；现有有界补读可以承接更小的实现。

[Anthropic 官方上下文工程文档](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 的 Compaction 部分强调先保留关键信息，再消除冗余，并提醒过强压缩会丢掉稍后才显现重要性的细节。这是工程原则，不是已经证明本项目的对象关联方案有效。

ReasoningBank、SkillFlow 的学习器真实输入、截断与限制见 [long-traces.md](long-traces.md)；SkillSmith、GEPA 的反馈构造和准入分离见 [feedback-and-validation.md](feedback-and-validation.md)。本次使用 web 检索和第二搜索引擎交叉发现资料；第二引擎首轮泛化查询偏离主题，精确题名后命中 RLM 论文与作者页面，结论只依据原始来源。

## 第 3–5 项如何衔接

- 经验与 Skill：先保存范围明确、有证据的观察或假设；具备可复用触发条件和具体行为变化时提出 Skill 候选。单轨迹能提出候选，不能独自证明稳定收益；补齐证据也不自动要求新增 Skill，应检查已有适用 Skill。
- 准入与研究：任务正确性、硬约束、回归和预算检查用于采用决定；“是否按预想顺序推理”等研究问题要另列，尤其不能要求不可见的内部推理。规则在比较前冻结，不能为已失败候选事后删门。已经失败的质量/回归不会因移走研究性检查而变成通过。
- 执行器与对照：先固定 Actor 的工具能力、预算和提示，再比较无记忆/已有固定 Skill/演化 Skill。在同任务做配对重复，记录方差和维护成本；不能把修复 Actor 后的提升计入记忆收益。本轮没有实施这些新对照。

建议调整顺序是可信反馈粒度与完整判断材料 → 提炼/诊断提示词和经验门槛 → 候选准入及配对执行。复杂 Skill 关系评分或多候选搜索可以保留为既有机制，但它们无法补回未进入模型的事实。
